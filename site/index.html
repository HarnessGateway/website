Professional services

We build the agents. You keep the platform.

The hard part of an agent is rarely the model. It is the packaging, the permissions, the review step and the place it runs. We work alongside your team to get one agent into real use, then the next.

1

Find the right first job

We look at where your people spend time on work an agent can draft: follow-ups, reports, research, content. We pick one job with a clear owner and a way to check the result.

2

Build the worker

Each agent is a package: the agent CLI, its standing instructions, its permission rules, the hosts it may reach and the output your application reads. You get the source.

3

Put it in the tools you use

The agent works inside your own application through one API. It drafts; a person reviews and approves what goes out.

4

Run it in your environment

We deploy the platform on your infrastructure, on one Linux host or on Kubernetes. Your data and your model provider keys stay with you.

Everything we build is yours: the packages, the application code, and an open-source platform with no licence fee. And because the platform is not tied to one agent harness, your agents can move to a better one when it arrives.

The open-source core

One API in front of any agent harness, with a sandbox around each session.

HarnessGateway is the platform under every engagement, and it is yours to run without us. Your application sends a standard request; the platform runs it through an agent package in a sandbox and streams the work back.

  1. Your applicationsends an OpenAI Responses request
  2. APIchecks the caller and queues the turn
  3. Boxone sandbox per session runs the agent package
  4. Doorthe only way out: your allow list, credentials added here
  5. Model providerand the hosts you allowed, with your own keys

One API

The OpenAI Responses schema in both directions. Any OpenAI SDK works unchanged, and previous_response_id continues a session.

Switch harnesses freely

Each agent harness is a package: a manifest and two executables. Your application picks one by name in model, so moving from Claude Code to Codex, pi or the next harness is a one-line change.

A sandbox per session

Every session runs in its own gVisor sandbox with no route out except the door, which enforces your allow and deny entries.

No secret enters the sandbox

Provider keys and other credentials are placeholders inside. The real values are added at the door, only toward the hosts they belong to.

Sessions that survive

After each turn the sandbox saves what changed. A session resumes in a new sandbox from where it stopped.

Metered and traced

Agent time, CPU, memory, network and storage are recorded per organization. Every run, connection and provider call is traced.

Self-host

Running in a few minutes on one Linux machine.

You need a Linux machine with Docker Engine; the installer adds the gVisor sandbox for you. It starts the platform, creates your organization and prints your admin invitation.

git clone https://github.com/HarnessGateway/harnessgateway
cd harnessgateway
sudo ./deploy/install.sh
