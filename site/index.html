Professional services

We build the agents. You keep the platform.

The hard part of an agent is rarely the model. It is the packaging, the permissions, the review step and the place it runs. We work alongside your team to get one agent into real use, then the next.

1

Find the right first job

We look at where your people spend time on work an agent can draft: follow-ups, reports, research, content. We pick one job with a clear owner and a way to check the result.

2

Build the worker

3

Put it in the tools you use

The agent works inside your own application through one API. It drafts; a person reviews and approves what goes out.

4

Run it in your environment

We deploy the platform on your infrastructure: one host with Docker, or Kubernetes with the enterprise edition. Your data and your model provider keys stay with you.

Everything we build is yours: the packages, the application code, and an open-source platform with no licence fee. And because the platform is not tied to one agent harness, your agents can move to a better one when it arrives.

The open-source core

One API in front of any agent harness, with a sandbox around every turn.

HarnessGateway is the platform under every engagement, and it is yours to run without us. Your application sends a standard request; the platform runs the harness CLI in a sandbox and streams the work back.

  1. Your applicationsends an OpenAI Responses request
  2. APIchecks the key and queues the turn
  3. Sandboxa fresh one per turn; the session's files are put back, the harness CLI runs
  4. Egress proxythe only way out: your network policy, secrets added here
  5. Model providerand the hosts you allowed, with your own keys

One API

The OpenAI Responses API, unchanged: streaming, background, previous_response_id, Files and Containers. Any OpenAI SDK works. No added fields.

Switch harnesses freely

Each harness is a package: harness.json, install and run. Your application picks one in model. Switch mid-session and the next harness takes over the same files.

A sandbox per turn

Every turn runs in a fresh sandbox you define: an image, limits and a network policy. With gVisor it does not share the host's kernel.

No secret enters the sandbox

The sandbox holds placeholders. The egress proxy puts the real value into requests, only toward the hosts a secret is bound to.

Sessions that survive

A session keeps the agent's home directory and its working directory. Both are saved after every turn and put back before the next.

A trace of every turn

The command that ran, its output, what it cost in tokens and time, and every host it reached.

Self-host

Running in a few minutes on one machine.

You need one machine with Docker. The installer starts the platform and prints the console's address and your first admin key. On a Linux host, --with-gvisor keeps sandboxes off the host's kernel.

curl -fsSL https://raw.githubusercontent.com/HarnessGateway/harnessgateway/main/deploy/install.sh | bash
